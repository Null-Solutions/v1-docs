Null V1 has two routers with the same market-operation signatures and different oracle fee models:

| Contract              | Use for                | Fee model                                    |
| --------------------- | ---------------------- | -------------------------------------------- |
| `NullV1Router`        | Chainlink Data Streams | Fee-less `update(bytes[])`                   |
| `NullV1PayableRouter` | Pyth                   | Pays native update fees from its ETH balance |

`NullV1Router` is stateless, ownerless, and nonpayable. `NullV1PayableRouter` is owned because its owner manages the ETH used for oracle updates.

User-facing `createMarket`, `depositMarket`, and `redeemMarket` calls are not payable. Do not attach `msg.value`.

## Payable router ETH operations

```solidity
receive() external payable;

function withdrawEth(address to, uint256 amount) external;

event WithdrawEth(address indexed to, uint256 amount);
```

Anyone can send ETH directly to the payable router. Only its owner can call `withdrawEth`. The withdrawal reverts for a zero recipient, insufficient router balance, failed ETH transfer, or unauthorized caller.

For a nonempty oracle payload, the payable router reads `getUpdateFee(updateData)` and pays exactly that amount from its existing balance. It reverts with `InsufficientUpdateFeeBalance(balance, required)` when underfunded.

## Oracle update data

The routers apply nonempty `updateData` before market creation, deposit, or redemption:

- `NullV1Router` calls the fee-less `update(updateData)` interface.
- `NullV1PayableRouter` calls the payable update interface using its own ETH.

Fetch and encode data according to the selected oracle:

- [Pyth update data](/contracts/oracles/pyth#update-data)
- [Chainlink update requirements](/contracts/oracles/chainlink#nonpayable-fee-zero-routing)

Pass `[]` only when the stored oracle price is usable. The fee-less router cannot pay a Pyth update fee.

## Create market

```solidity
function createMarket(
    INullV1Factory factory,
    IERC20 collateral,
    INullV1Oracle oracle,
    INullV1FundingRateModel frm,
    bytes[] calldata updateData
) external returns (INullV1Market market);
```

The router optionally updates the oracle, then calls the supplied factory. It does **not** verify that the factory is a canonical Null deployment. Copy the factory from [Ethereum deployments](/resources/addresses) once published and validate untrusted configuration. Do not substitute an address from another network.

The factory requires nonzero dependencies, an enabled FRM, a nonzero initial oracle price, and an unused `(collateral, oracle, frm)` tuple.

## Deposit

```solidity
function depositMarket(
    INullV1Market market,
    uint256 receiverAssets,
    uint256 payerAssets,
    uint256 minReceiverShares,
    uint256 minPayerShares,
    uint256 deadline,
    bytes[] calldata updateData
) external returns (uint256 receiverShares, uint256 payerShares);
```

Flow:

1. Check `deadline`
2. Optionally update the oracle
3. Pull collateral (wrapping ERC-4626 underlying when needed)
4. Deposit into each side where assets `> 0`
5. Enforce `minReceiverShares` / `minPayerShares`

Reverts: `TransactionTooOld`, `SlippageReceiverShares`, `SlippagePayerShares`.

## Redeem

```solidity
function redeemMarket(
    INullV1Market market,
    uint256 receiverShares,
    uint256 payerShares,
    uint256 minReceiverAssets,
    uint256 minPayerAssets,
    uint256 deadline,
    bytes[] calldata updateData
) external returns (uint256 receiverAssets, uint256 payerAssets);
```

Flow:

1. Check `deadline`
2. Optionally update the oracle
3. Redeem each side where shares `> 0`
4. Push collateral (unwrapping ERC-4626 when needed)
5. Enforce asset minimums

Reverts: `TransactionTooOld`, `SlippageReceiverAssets`, `SlippagePayerAssets`.

The router redeems pool shares owned by `msg.sender`. The caller must approve the router to spend each active Receiver or Payer pool token.

## Collateral detection and units

The router probes `market.collateral().asset()` using the ERC-4626 interface:

| Probe result                        | Deposit amounts   | Redeem results and minimums |
| ----------------------------------- | ----------------- | --------------------------- |
| `asset()` succeeds                  | Vault underlying  | Vault underlying            |
| `asset()` reverts or is unavailable | Market collateral | Market collateral           |

A successful `asset()` call selects the vault path. The router does not fall back if a later underlying transfer, vault deposit, or vault redeem fails.

For ERC-4626 collateral:

```text
deposit: underlying → collateral vault shares → Null pool shares
redeem:  Null pool shares → collateral vault shares → underlying
```

Use `collateralVault` and `underlying` in generic integration code. Resolve both from canonical market configuration and `collateralVault.asset()`; do not assume a particular token pair.

## Approvals

| Collateral type      | Approve router to spend                     |
| -------------------- | ------------------------------------------- |
| Plain ERC-20         | Market collateral                           |
| ERC-4626 vault share | Vault **underlying**                        |
| Redeem               | Receiver and/or Payer **pool share** tokens |

Approve the sum of active Receiver and Payer deposit amounts. For redemption, approve each pool token independently.

## Slippage and deadlines

Use one convention across deposits and redemptions:

```ts
const BPS = 10_000n;
const slippageBps = 50n; // 0.50%

function applySlippageFloor(quotedOutput: bigint): bigint {
  return (quotedOutput * (BPS - slippageBps)) / BPS;
}
```

Apply it to the final output unit:

- deposit: final Receiver or Payer pool shares;
- redeem with plain collateral: market collateral;
- redeem with ERC-4626 collateral: vault underlying.

Set the amount and minimum to zero for a skipped side. A zero minimum on an active side disables protection.

`deadline` is Unix time in seconds. Calls revert with `TransactionTooOld(deadline)` only when `block.timestamp > deadline`.
