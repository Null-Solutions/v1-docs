Every market deploys two `NullV1Pool` clones. They implement ERC-4626 while delegating collateral custody and settlement accounting to their market.

## Kind and naming

```solidity
enum NullV1PoolKind {
    Receiver, // 0
    Payer     // 1
}

function market() external view returns (INullV1Market);
function poolKind() external view returns (NullV1PoolKind);
```

Names and symbols come from the market oracle:

| Kind | Name | Symbol |
|---|---|---|
| `Receiver` | `<baseName> Receiver Share` | `<baseSymbol>r` |
| `Payer` | `<baseName> Payer Share` | `<baseSymbol>p` |

The side letter is a suffix: an oracle with base symbol `AAPL` gives `AAPLr` and `AAPLp`.

An empty oracle base name falls back to `Base`; an empty base symbol falls back to `BASE`.

## ERC-4626 accounting

```solidity
function totalAssets() public view returns (uint256);
```

`totalAssets()` reads the corresponding `receiverPool` or `payerPool` amount from the market's last settled state. The value is denominated in market collateral units and does not itself trigger settlement.

The pool's decimals offset is `2`. OpenZeppelin ERC-4626 therefore reports share decimals as `collateral.decimals() + 2` (20 for 18-decimal collateral) and includes `10^2` virtual shares in conversion math. The offset is kept small so the Receiver share stays a valid Morpho Blue loan token: Blue stores supply and borrow shares in `uint128`. Use ERC-4626 conversion and preview functions; do not assume assets and shares use the same decimals.

## Entry points

Only the assets-in entry and the shares-in exit are live:

```solidity
function deposit(
    uint256 assets,
    address receiver
) public returns (uint256 shares);

function redeem(
    uint256 shares,
    address receiver,
    address owner
) public returns (uint256 assets);
```

`mint(shares, receiver)` and `withdraw(assets, receiver, owner)` are permanently disabled and revert with `NotImplemented()`. An exact-shares entry cannot charge the same notional fee as `deposit` for the same gross amount, so only `deposit` and `redeem` are offered.

Before conversion, `deposit` and `redeem` lock the market's reentrancy guard and call `market.updateState()`. Deposits transfer collateral directly from the caller to the market; redemptions are paid by the market. If the caller redeems another owner's shares, the owner must approve the caller.

A nonzero deposit that would mint zero shares reverts with `ZeroShares()`. This happens when the entry fee consumes the whole amount (at an extreme `R / P`).

Entry and exit fees are sized on settleable-R notional (`assets × settleableR / ownAssets`), not on collateral alone. Entry fees are included in the `assets` paid by depositors and excluded from assets converted into shares. Exit fees are deducted from redeemed assets. The fee is `min(assets, ceil(notional × feeBps / (10000 + feeBps)))`. Receiver-pool fees credit the Payer pool (or the Receiver pool itself while the Payer pool is at or below `MIN_POOL_ASSETS`). Payer-pool fees credit `protocolFees`. See [Fees](/protocol/fees).

## Previews

```solidity
function previewDeposit(uint256 assets) public view returns (uint256 shares);
function previewRedeem(uint256 shares) public view returns (uint256 assets);
```

`previewMint` and `previewWithdraw` revert with `NotImplemented()`, matching the disabled `mint` and `withdraw`.

`previewDeposit` and `previewRedeem` include entry or exit fees and use the market's **last settled state**. Execution settles funding, balance changes, and price PnL first, so a stale market can produce materially different results. This is an accepted deviation from strict ERC-4626 preview semantics.

<Warning>
Use `NullV1Lens.previewMarket` for a settlement-accurate state projection, then enforce `minReceiverShares`, `minPayerShares`, `minReceiverAssets`, or `minPayerAssets` through the appropriate router.
</Warning>

## Max functions

```solidity
function maxDeposit(address) public view returns (uint256);
function maxMint(address) public pure returns (uint256);     // 0
function maxWithdraw(address) public pure returns (uint256); // 0
function maxRedeem(address owner) public view returns (uint256);
```

- `maxDeposit` depends on the pool kind. The Payer pool returns `type(uint256).max`. The Receiver pool returns the room left under the pool ratio cap: `MAX_POOL_RATIO × payerPool − receiverPool`, or `0` when the Receiver pool is already at or above the cap. It does not reflect wallet balances.
- `maxMint` and `maxWithdraw` always return `0`. This is the ERC-4626 signal that `mint` and `withdraw` are disabled; check it before calling them.
- `maxRedeem(owner)` depends on the pool kind. The Receiver pool returns `balanceOf(owner)`. The Payer pool returns `balanceOf(owner)` capped by the shares the pool ratio cap lets out, which can be `0`.

## Pool ratio cap

A deposit or redemption may not leave the Receiver pool larger than `MAX_POOL_RATIO` times the Payer pool. `MAX_POOL_RATIO` is `5`:

```text
receiverPool <= 5 × payerPool
```

Only two flows raise `R / P`, and only those two are limited:

| Flow | Effect on `R / P` | Limit |
|---|---|---|
| Receiver deposit | Raises it | At most `5 × payerPool − receiverPool` assets. Reverts with `ERC4626ExceededMaxDeposit`. |
| Payer redemption | Raises it | Must leave `payerPool >= ceil(receiverPool / 5)`. Reverts with `ERC4626ExceededMaxRedeem`. |
| Payer deposit | Lowers it | None. |
| Receiver redemption | Lowers it | Only the owner's share balance. |

Details that matter for integrations:

- An empty market takes Payer deposits first. With an empty Payer pool, `maxDeposit` on the Receiver pool is `0`.
- The Receiver limit ignores the entry fee, so it is slightly conservative when the fee goes to the Payer pool.
- The Payer limit is on gross assets (the net amount plus the exit fee), because that is what leaves the Payer pool.
- The Payer limit is off while the Receiver pool holds at most `MIN_POOL_ASSETS`. Nothing settles then, so the last Payer can always exit in full.
- Settlement (price PnL and funding) can still push `R / P` above `5`. While it is above, Receiver deposits and Payer redemptions are closed. A Payer deposit or a Receiver redemption brings the ratio back down and is always allowed.
- `maxDeposit` and `maxRedeem` read the last settled state. `deposit` and `redeem` settle first and then enforce the limit, so the enforced value can differ from the view on a stale market.

## Errors

| Error | Condition |
|---|---|
| `NotImplemented()` | `mint`, `withdraw`, `previewMint`, or `previewWithdraw` is called. |
| `ZeroShares()` | A nonzero deposit would mint zero shares. |
| `ERC4626ExceededMaxDeposit(address receiver, uint256 assets, uint256 max)` | A Receiver `deposit` would push the Receiver pool above the [pool ratio cap](#pool-ratio-cap). |
| `ERC4626ExceededMaxRedeem(address owner, uint256 shares, uint256 max)` | `redeem` asks for more shares than the owner holds, or a Payer `redeem` would leave the Payer pool below the [pool ratio cap](#pool-ratio-cap). |

Pools emit the standard ERC-20 `Transfer` and ERC-4626 `Deposit` and `Withdraw` events. `Withdraw` is emitted by `redeem`.
