Building a reliable indexer for Null V1 means listening to a small set of well-defined events and supplementing them with off-chain view calls via `NullV1Lens`. Because user positions are represented entirely as ERC-20 share token balances — with no separate position struct — your indexing logic stays straightforward: discover markets from the factory, record state snapshots from each market, and follow standard `Transfer` events on the two pool share tokens per market.

## Architecture Overview

A Null V1 indexer needs three data feeds per market:

1. **Market discovery** — watch `NullV1Factory` for `MarketCreated` to learn about new markets.
2. **Market state history** — index `StateUpdated` events emitted by each `NullV1Market` to build pool balance and price history.
3. **User position history** — track ERC-20 `Transfer` events on the `receiverPool` and `payerPool` share tokens to reconstruct each user's balance over time.

The `NullV1Lens` contract provides a convenient off-chain read layer for current state without requiring a subgraph or local replay.

## Step-by-Step Indexing Guide

<Steps>

### Watch NullV1Factory for MarketCreated

Every new Null V1 market is announced by a single factory event. Subscribe to this event at the factory deployment block and process all historical logs at startup.

```solidity
// NullV1Factory
event MarketCreated(
    address indexed asset,
    address indexed oracle,
    uint24 indexed mu,
    address market,
    address receiverPool,
    address payerPool
);
```

When you receive a `MarketCreated` event, persist **all six fields**. You will need both `receiverPool` and `payerPool` addresses immediately to set up Transfer event listeners for user position tracking.

<Note>
  Store `receiverPool` and `payerPool` addresses as soon as `MarketCreated` fires. If you defer this step you will miss early Transfer events and your position history will be incomplete.
</Note>

### Index StateUpdated Events for Pool and Price History

Each `NullV1Market` emits `StateUpdated` on every meaningful state transition — deposits, redeems, and periodic settlement ticks. These events are the canonical source of truth for pool balance and price history.

```solidity
// NullV1Market
event StateUpdated(
    uint256 indexed timestamp,
    uint256 receiverPoolAssets,
    uint256 payerPoolAssets,
    uint256 price,
    uint256 protocolFees,
    uint256 sharePrice
);
```

Index these events per market address and store each field. A few important unit notes:

- `price` is **1e36-scaled**. To convert to a human-readable price divide by `1e36`.
- `receiverPoolAssets` and `payerPoolAssets` are denominated in the collateral token units (or wrapper units if the collateral is an ERC-4626 vault).
- For ERC-4626 collateral, multiply pool units by `wrapper.convertToAssets(1e18)` (then divide by `1e18`) to express balances in underlying token terms.

<Tip>
  Persist raw 1e36-scaled price values in your database and convert to display units at query time. This avoids precision loss and keeps your stored data consistent with on-chain values.
</Tip>

Also subscribe to the fee events if you want to track configuration changes:

```solidity
event FeesUpdated(uint16 entryFee, uint16 exitFee, uint16 yieldFee);
event FeesCollected(uint256 fee);
```

### Track User Positions via Transfer Events

Null V1 has no dedicated position struct. A user's position in the receiver or payer pool **is** their ERC-20 share token balance on `receiverPool` or `payerPool` respectively. Index standard ERC-20 Transfer events on both pool addresses:

```solidity
// NullV1Pool (ERC-4626 share token — standard ERC-20)
event Transfer(address indexed from, address indexed to, uint256 value);
```

Apply the same balance-delta logic you would for any ERC-20:

- `from == address(0)` → mint (deposit)
- `to == address(0)` → burn (redeem)
- Otherwise → transfer between accounts

You can cross-reference with the ERC-4626 `Deposit` and `Withdraw` events for richer context (e.g. the `assets` amount involved in a mint or burn):

```solidity
// NullV1Pool (ERC-4626 standard events)
event Deposit(
    address indexed caller,
    address indexed owner,
    uint256 assets,
    uint256 shares
);
event Withdraw(
    address indexed caller,
    address indexed receiver,
    address indexed owner,
    uint256 assets,
    uint256 shares
);
```

<Note>
  Remember to subscribe to Transfer events on **both** `receiverPool` and `payerPool` for every market. A user may hold positions in one or both pools.
</Note>

### Use NullV1Lens for Current State

`NullV1Lens` provides a single call that aggregates current market state for off-chain callers. Use it to power live dashboards without replaying all historical events.

```solidity
struct SimulateResponse {
    MarketState state; // {timestamp, receiverPool, payerPool, price, protocolFees, sharePrice}
    uint256 totalAssets;
    uint256 receiverTotalSupply;
    uint256 payerTotalSupply;
    uint256 fundingApr; // WAD-scaled (1e18 = 100%)
}

function previewMarket(address market)
    external
    view
    returns (SimulateResponse memory);

function simulateMarket(address market, uint256 price)
    external
    view
    returns (SimulateResponse memory);
```

Call `previewMarket(market)` to get the current on-chain state. Call `simulateMarket(market, price)` to project what state would look like at an arbitrary price — useful for scenario displays.

<ResponseField name="state.price" type="uint256">
  The current oracle price, 1e36-scaled. Divide by `1e36` to get a human-readable value.
</ResponseField>

<ResponseField name="fundingApr" type="uint256">
  WAD-scaled (1e18 = 100%). Divide by `1e18` then multiply by 100 to get a percentage string, e.g. `3e16 / 1e18 * 100 = 3%`.
</ResponseField>

<ResponseField name="state.sharePrice" type="uint256">
  The current share price in collateral units. Useful for historical share price charts.
</ResponseField>

To resolve a user's current asset value at query time without relying solely on indexed data:

```solidity
uint256 shares = pool.balanceOf(user);
uint256 assets = pool.previewRedeem(shares);
```

### Use Oracle Metadata for Display Names

Each `NullV1Market` exposes an oracle that implements a standard metadata interface. Pull these values when you first discover a market and cache them — they rarely change.

```solidity
oracle.oracleName()    // e.g. "Pyth"
oracle.baseName()      // e.g. "Apple Inc."
oracle.baseSymbol()    // e.g. "AAPL"
oracle.quoteName()     // e.g. "US Dollar"
oracle.quoteSymbol()   // e.g. "USD"
oracle.displayName()   // bytes32 display key, e.g. keccak256("PYTH_CORE_PULL")
```

A human-readable market label is typically `baseSymbol / quoteSymbol` (e.g. `AAPL / USD`), while `baseName` and `quoteName` suit longer descriptions.

</Steps>

## Unit Reference

| Field | Scale | Human Conversion |
|---|---|---|
| `StateUpdated.price` | 1e36 | `price / 1e36` |
| `StateUpdated.receiverPoolAssets` | Collateral token units | Multiply by `convertToAssets(1e18) / 1e18` for ERC-4626 collateral |
| `StateUpdated.payerPoolAssets` | Collateral token units | Same as above |
| `SimulateResponse.fundingApr` | WAD (1e18 = 100%) | `fundingApr / 1e18 * 100` → percent |
| `SimulateResponse.state.sharePrice` | Collateral token units | Display as-is or convert for ERC-4626 |

## ABI and Bytecode Artifacts

After making contract changes, regenerate ABI and Lens bytecode artifacts so your indexer always has up-to-date ABIs and can perform off-chain simulation calls using the deployed bytecode.

```bash
forge build
npm run codegen
```

`codegen` exports the Lens bytecode to:
- `src/generated/lens-bytecode.ts`
- `../v1-indexer/src/utils/lens-bytecode.ts`

Use the deployed Lens bytecode with `eth_call` (no deployment required) for off-chain state simulation.
