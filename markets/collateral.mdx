Null V1 markets accept two categories of collateral: plain ERC-20 tokens and non-rebasing ERC-4626 yield-bearing wrappers. The distinction matters because the protocol tracks pool balances in the units of whatever token is deposited — if that token accrues value internally (as ERC-4626 wrappers do), both pool participants passively earn the underlying yield on top of their funding cashflows. Choosing the right collateral type for your market affects everything from user experience to the net APR arithmetic, so this page walks through both options and their tradeoffs.

---

## Plain ERC-20 Collateral

Any standard ERC-20 token can serve as collateral for a Null V1 market. There is no whitelist — the factory accepts any non-zero address. Plain ERC-20 collateral markets are the simplest to reason about: pool balances are static (they do not grow unless funding is accruing), and the oracle price is the only thing that shifts economics over time.

  <Card title="Examples" icon="coins">
    - USDC
    - WETH
    - DAI
    - WBTC
    - Any non-rebasing ERC-20
  </Card>
  <Card title="Characteristics" icon="list-check">
    - Pool balances denominated in token units
    - No passive yield for LPs
    - `yieldFee` has no effect
    - Simplest integration path
  </Card>
</CardGroup>

## ERC-4626 Yield-Bearing Wrappers

When a market is created with an ERC-4626 compliant vault token as collateral, liquidity providers passively earn the vault's underlying yield on top of their funding cashflows. The protocol holds balances in **wrapper units** (also called "shares"), not in the underlying asset. Because the share price grows over time, the effective value of each LP's position increases without any on-chain accounting changes in the protocol itself.

<CardGroup cols={2}>
  <Card title="Examples" icon="coins">
    - `waUSDC` (wrapped Aave USDC)
    - `wstETH` (wrapped staked ETH)
    - Any non-rebasing ERC-4626 vault
  </Card>
  <Card title="Characteristics" icon="list-check">
    - Pool balances denominated in share units
    - Passive yield accrues inside the token
    - `yieldFee` takes a cut of yield for the protocol
    - Oracle is unaffected by share price
  </Card>
</CardGroup>

### How Yield-Bearing Collateral Works

Because the protocol stores balances in wrapper (share) units rather than underlying asset units, yield accrues automatically:

1. A user deposits `waUSDC` shares into a pool.
2. The pool records the deposit in share units.
3. Over time, each `waUSDC` share is redeemable for more USDC (the Aave lending yield accrues).
4. When the user withdraws, they receive more USDC-equivalent value than they deposited — without any protocol-level accounting for the yield.

<Note>
  The oracle does not need to account for the share price of the wrapper. Null
  V1 oracles price the **underlying asset** (e.g. AAPL in USD), not the wrapper
  token. The wrapper's share-price growth is entirely separate from the oracle's
  responsibility.
</Note>

### Net Carry for LPs in Yield-Bearing Markets

With yield-bearing collateral, the net annual return for each side of the pool combines the wrapper's underlying yield with the funding cashflow:

| Role | Net APR Formula |
|------|----------------|
| **Receiver LP** | `yieldAPR − fundingAPR` |
| **Payer LP** | `yieldAPR + fundingAPR × rho` |

Where `fundingAPR = mu / 1_000_000 × rho` and `yieldAPR` is the underlying yield of the ERC-4626 wrapper.

<Tip>
  For receiver LPs, yield-bearing collateral can partially or fully offset the
  funding cost. For example, if `waUSDC` yields 5% and the funding rate is 3%,
  the net cost to receivers is only 2%. Payers benefit even more: they earn both
  yield and the amplified funding payment.
</Tip>

## Rebasing Tokens Are Not Supported

Tokens that implement rebasing — where the holder's **balance** changes directly rather than through an exchange rate — are **not compatible** with Null V1. The protocol cannot correctly track pool balances when the token itself silently adjusts them.

<Warning>
  Do **not** use raw rebasing tokens as collateral (e.g. `aUSDC` from Aave v2,
  `stETH` from Lido). The protocol will not function correctly because pool
  share accounting assumes token balances only change through explicit
  deposits and withdrawals.
</Warning>

### What to Do Instead

Wrap the rebasing token in a non-rebasing ERC-4626 compatible vault before using it as collateral. Most major DeFi protocols provide official wrappers:

| Rebasing Token | Non-Rebasing Wrapper |
|---|---|
| `aUSDC` (Aave v2) | `waUSDC` (Aave v3 wrapped) |
| `stETH` (Lido) | `wstETH` (Lido wrapped) |
| `aDAI` (Aave v2) | `waDAI` (Aave v3 wrapped) |

The wrapper handles the rebase internally, exposing a stable balance interface to the protocol while preserving all the yield for token holders.

## Depositing and Withdrawing

Users always deposit and withdraw the **wrapper token directly**. The protocol itself does not perform any wrapping or unwrapping. If you want to give end users the ability to deposit the underlying asset (e.g. deposit raw USDC instead of `waUSDC`), you can build a UI layer that wraps on their behalf before calling the pool.

<Note>
  The Null V1 Router supports auto-unwrapping ERC-4626 collateral when users
  withdraw. When a user exits a pool that holds ERC-4626 shares, the router can
  redeem the shares and return the underlying token to the user in a single
  transaction, improving UX without requiring the user to manually interact with
  the vault contract.
</Note>

## Choosing Collateral: Summary

<CardGroup cols={2}>
  <Card title="Use plain ERC-20 when..." icon="circle-check">
    - The market does not need passive yield
    - You want the simplest possible integration
    - The asset has no natural yield wrapper (e.g. WBTC)
    - You want `yieldFee` to be a no-op
  </Card>
  <Card title="Use ERC-4626 wrapper when..." icon="circle-check">
    - You want LPs to earn underlying yield (e.g. lending yield)
    - You are building a stablecoin-denominated market on a yield-bearing stablecoin
    - You want to partially offset the funding cost for receiver LPs
    - The protocol taking a `yieldFee` is acceptable
  </Card>
</CardGroup>
