# Pools and ERC-4626

Each Null V1 market owns two `NullV1Pool` contracts:

- Receiver pool
- Payer pool

Both pools implement ERC-4626. The share token represents a proportional claim on that pool's current market-recorded assets.

## Pool kind

Use `poolKind()` to identify a pool:

```solidity
enum NullV1PoolKind {
    Receiver,
    Payer
}

function poolKind() external view returns (NullV1PoolKind);
```

Use `market()` to find the market that owns the pool:

```solidity
function market() external view returns (INullV1Market);
```

## Source of truth for assets

`totalAssets()` reads the market state:

```solidity
function totalAssets() public view returns (uint256) {
    (, uint256 receiverPoolAssets, uint256 payerPoolAssets,,,) = _market.state();
    return _poolAssetsForKind(receiverPoolAssets, payerPoolAssets);
}
```

The pool does not compute price settlement or funding. The market owns accounting, and the pool exposes ERC-4626 share math against the current market-recorded pool value.

## State updates before actions

The pool calls `market.updateState()` before every state-changing ERC-4626 action:

```solidity
deposit(assets, receiver)
mint(shares, receiver)
withdraw(assets, receiver, owner)
redeem(shares, receiver, owner)
```

This means execution share math is based on the post-update pool value, not necessarily the value observed during an earlier preview call.

## Preview functions

The pools override ERC-4626 previews to include entry and exit fees.

```solidity
previewDeposit(assets)  // deposit path, fee-on-total
previewMint(shares)     // mint path, fee-on-raw
previewWithdraw(assets) // withdraw path, fee-on-raw
previewRedeem(shares)   // redeem path, fee-on-total
```

Previews are useful for UI estimates, but they are not execution guarantees. Between preview and execution:

- the oracle price can change;
- time can pass and funding can accrue;
- collateral balances can reconcile;
- fees can change;
- another user can enter or exit.

Use slippage limits for user transactions.

## Fee paths

Null follows the ERC-4626 fee patterns:

- `deposit`: fee-on-total. The user's `assets` amount includes the entry fee.
- `mint`: fee-on-raw. The user pays enough assets to mint the requested shares plus the entry fee.
- `withdraw`: fee-on-raw. The pool removes the requested assets plus the exit fee.
- `redeem`: fee-on-total. The redeemed assets include the exit fee, and the user receives the net amount.

Entry and exit fees leave the Receiver/Payer pool system and are routed to the protocol owner.

## Asset transfer flow

On deposit, the pool:

1. updates the market state;
2. transfers assets from the caller to the market;
3. records the net deposit on the market;
4. mints pool shares to the receiver.

On withdrawal or redemption, the pool:

1. updates the market state;
2. asks the market to transfer assets to the receiver;
3. records the gross pool deduction and fee;
4. burns shares from the owner.

## Share value

To estimate a user's current value in one pool:

```text
userValue = pool.balanceOf(user) * pool.totalAssets() / pool.totalSupply()
```

Handle `totalSupply() == 0` carefully in offchain calculations.

Because `totalAssets()` can change when the next state update runs, offchain values are snapshots, not guaranteed execution amounts.

## Direct pool calls versus router calls

Direct pool calls are best when:

- the market asset is the token the user already holds;
- you only need one pool action;
- you handle approvals, slippage, and oracle update requirements yourself.

Router calls are best when:

- you want to deposit or redeem both sides in one transaction;
- you need deadline and slippage checks;
- the market uses an updatable oracle and needs `updateData`;
- the market asset is an ERC-4626 vault share and users interact in the underlying asset.
