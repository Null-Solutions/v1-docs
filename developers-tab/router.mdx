Null V1 provides two periphery routers with the same market-operation signatures:

- `NullV1Router` is stateless and ownerless. It calls fee-less oracle updates without forwarding ETH and is the correct choice for Chainlink Data Streams markets.
- `NullV1PayableRouter` is Ownable and pre-funded with ETH. It pays an oracle's native update fee from its own balance and is the correct choice for Pyth markets.

Neither router owns core market accounting.

Use the router when you need:

- combined Receiver and Payer deposits;
- combined Receiver and Payer redemptions;
- deadline checks;
- minimum share or asset checks;
- push-oracle `updateData`;
- ERC-4626 collateral wrapping and unwrapping.

## Choose a router

Router methods accept:

```solidity
bytes[] calldata updateData
```

If `updateData.length > 0`, `NullV1Router` calls the fee-less updater:

```solidity
INullV1UpdatableOracle(address(oracle)).update(updateData);
```

`NullV1PayableRouter` instead queries and pays the native fee:

```solidity
uint256 fee = updatable.getUpdateFee(updateData);
updatable.update{value: fee}(updateData);
```

If its balance is insufficient, the payable router reverts with `InsufficientUpdateFeeBalance`. Its owner can recover unused ETH with `withdrawEth`; users do not attach `msg.value` to market operations.

If the oracle does not require push updates, pass an empty array.

## Create market

```solidity
function createMarket(
    INullV1Factory factory,
    IERC20 collateral,
    INullV1Oracle oracle,
    INullV1FundingRateModel frm,
    bytes[] calldata updateData
) external returns (INullV1Market market);
```

This optionally updates the oracle, then calls:

```solidity
factory.createMarket(collateral, oracle, frm)
```

The factory requires nonzero dependencies, an enabled FRM, and a previously unused `(collateral, oracle, frm)` tuple.

## Deposit market

```solidity
function depositMarket(
    INullV1Market market,
    uint256 receiverAssets,
    uint256 payerAssets,
    uint256 minReceiverShares,
    uint256 minPayerShares,
    uint256 deadline,
    bytes[] calldata updateData
) external returns (uint256 receiverShares, uint256 payerShares);
```

The router:

1. checks `deadline`;
2. optionally updates the market oracle;
3. pulls collateral from the caller, wrapping ERC-4626 underlying when needed;
4. deposits into the Receiver pool if `receiverAssets > 0`;
5. deposits into the Payer pool if `payerAssets > 0`;
6. verifies returned shares against `minReceiverShares` and `minPayerShares`.

If returned shares are below the provided minimums, the call reverts with:

```solidity
SlippageReceiverShares(expected, actual)
SlippagePayerShares(expected, actual)
```

## Redeem market

```solidity
function redeemMarket(
    INullV1Market market,
    uint256 receiverShares,
    uint256 payerShares,
    uint256 minReceiverAssets,
    uint256 minPayerAssets,
    uint256 deadline,
    bytes[] calldata updateData
) external returns (uint256 receiverAssets, uint256 payerAssets);
```

The router:

1. checks `deadline`;
2. optionally updates the market oracle;
3. redeems Receiver shares if `receiverShares > 0`;
4. redeems Payer shares if `payerShares > 0`;
5. pushes collateral to the caller, unwrapping ERC-4626 collateral when needed;
6. verifies returned assets against `minReceiverAssets` and `minPayerAssets`.

If returned assets are below the provided minimums, the call reverts with:

```solidity
SlippageReceiverAssets(expected, actual)
SlippagePayerAssets(expected, actual)
```

## ERC-4626 collateral

Core markets hold their collateral token directly. If that token is an ERC-4626 vault share, the router accepts the vault underlying on deposit and returns the underlying on redemption.

On deposit:

1. the router pulls the vault underlying from the user;
2. deposits it into the ERC-4626 collateral vault;
3. deposits the received collateral shares into the selected Null pool.

On redemption:

1. the router redeems Null pool shares for collateral-vault shares;
2. redeems those shares from the ERC-4626 vault;
3. sends the underlying token to the user.

If the collateral does not expose `asset()`, the router treats it as a plain ERC-20.

## Deadlines

Deposit and redeem methods include:

```solidity
uint256 deadline
```

If `block.timestamp > deadline`, the transaction reverts with `TransactionTooOld`.

Use short deadlines for user-facing transactions so stale quotes do not execute unexpectedly.

## Approvals

For plain ERC-20 collateral, users approve the router to spend the collateral. For ERC-4626 collateral, users approve the router to spend the vault underlying.

## Operational notes

- Only `NullV1PayableRouter` holds ETH or pays native oracle update fees.
- Both routers are `nonReentrant` on deposit and redeem; payable-router withdrawals are also guarded.
- The router resets token approvals after wrapping and pool deposits.
- Router slippage checks happen after pool execution returns shares or assets.
- Core accounting still lives in the market and pools. The router is convenience periphery.
